# 插件驱动个性首页规划

> 状态:方案草案 · 更新于 2026-08-21
>
> 首期范围:iOS 首页、`AngelLiveCore` 首页数据协议与缓存；macOS / tvOS 暂不改入口
>
> 结论先行:**建议用插件驱动的个性首页替代当前默认收藏页。首页先展示缓存的插件内容和本地模块，收藏直播状态在后台独立刷新，既缩短首屏等待，也保留收藏入口。**
>
> 产品定位:**AngelLive 始终只是可扩展播放器工具。AngelLive 不提供、不维护、不分发插件，也不生产、筛选或推荐平台内容。插件由用户自行获取和安装，首页的平台内容完全来自用户已安装插件。**

---

## 0. 不可突破的产品边界

这一节是协议、产品文案和审核说明的共同前提，后续实现不得模糊。

1. **AngelLive 提供播放器与宿主能力，不提供内容。** 宿主负责插件运行、标准数据解码、缓存、原生 UI 渲染、播放和错误隔离。
2. **AngelLive 不提供插件。** 插件由用户独立获取、选择和安装；项目本身不内置平台插件，不提供或维护官方插件源，也不为第三方插件背书。宿主只管理用户自行配置的插件来源和安装结果。
3. **平台 Banner、榜单、推荐房间和推荐理由均由插件返回。** 宿主不得在没有插件数据时伪造平台推荐或用内置平台规则补齐。
4. **插件只返回数据，不能返回页面。** 不接受 HTML、WebView 页面、任意 SwiftUI 描述、脚本化布局或自定义动效；最终界面、交互和播放链路均由 AngelLive 原生实现。
5. **来源必须可识别。** 跨插件聚合时保留 `pluginId` 和插件显示名，界面可以按插件数据和产品设计展示来源信息，但不能写成“AngelLive 推荐”。
6. **“个性推荐”必须有事实依据。** 只有插件明确声明该分区为个性化结果时才显示“为你推荐”；普通聚合结果使用“推荐”“热门”或插件原始但经宿主校验的标题。
7. **宿主默认不向插件泄露跨插件行为。** 收藏、播放历史、其他插件的账号和内容偏好，不进入首页请求。插件如有个性化能力，应基于它自己的会话和数据源完成。
8. **责任边界不等于免责机制。** 插件及其数据仍需遵守适用规则；宿主保留禁用异常插件、限制危险字段和清理缓存的能力。

本文只使用“插件”“内容源”等通用称呼，示例数据使用中性占位内容，**不出现任何真实平台名称**。这是规划文档的匿名化要求，不是对插件返回内容、名称、Logo 或品牌信息的协议限制。

建议统一对外表述:

> AngelLive 是一个可扩展播放器工具。首页内容由用户自行安装的插件提供，AngelLive 仅负责标准化展示与播放。

## 1. 为什么要改首页

### 1.1 当前问题

当前 iOS 首个 Tab 是“收藏”，启动后即进入 `AdaptiveFavoriteView`。收藏模型虽然已经采用本地优先策略，但后续仍要刷新云端成员和逐个直播状态；平台接口慢、收藏数量多或某个插件异常时，用户会持续感知“首页还没刷新完”。

已确认的代码事实:

| 事实 | 当前实现 |
|---|---|
| 默认入口是收藏 | `iOS/AngelLive/AngelLive/ContentView.swift` 中 `selectedTab = .favorite` |
| 收藏会先显示本地数据 | `AppFavoriteModel.syncWithActor()` 先读取 `FavoriteLocalStore` |
| 收藏仍需后台刷新状态 | `refreshStatesAndApply(members:)` 调用插件刷新各房间状态 |
| 历史记录已经是本地数据 | `HistoryModel.watchList` 保存在共享 `UserDefaults`，最多 100 条 |
| 当前插件协议没有首页能力 | `PlatformFeature` 只有分类、房间、播放、搜索、详情、状态、分享解析和弹幕 |
| 插件运行时版本严格相等 | `LiveParseLoadedPlugin.load()` 要求插件 `apiVersion` 等于宿主支持版本 1 |

### 1.2 新首页要解决什么

- 启动时优先呈现可立即读取的内容，而不是让最慢的收藏状态刷新决定首屏体验。
- 首页以插件返回的 Banner 和推荐分区为主体，体现“播放器入口”而不是“同步状态页”。
- 收藏仍是首页的重要本地模块，并保留完整收藏页入口。
- 插件、收藏、历史各自加载和失败，任何一项都不能阻塞整页。
- 刷新期间保持卡片位置和滚动位置稳定，减少等待感和界面跳动。

### 1.3 首期体验指标

| 指标 | 目标 |
|---|---|
| 有缓存时首个有意义内容 | 冷启动后 300 ms 内出现本地/缓存内容 |
| 全屏 Loading | 有任一缓存或本地模块时不出现 |
| 插件失败影响范围 | 只影响该插件对应分区 |
| 收藏状态刷新 | 不阻塞 Banner、历史和推荐分区 |
| 刷新稳定性 | 不重置滚动位置，不因单张卡更新而整体重排 |
| 无插件状态 | 只展示本地工具能力和配置引导，不出现虚构推荐 |

这些数值是实施目标，需在真机和典型数据量下验证后再固化为发布门槛。

## 2. 首页信息架构

### 2.1 推荐的默认顺序

```text
首页
├─ 焦点 Banner                插件数据，缓存优先
├─ 我的收藏                   本地快照立即显示，状态静默刷新
├─ 插件推荐分区 1             插件数据，如“为你推荐”或“热门直播”
└─ 插件推荐分区 2...N         插件数据，按来源隔离
```

这个顺序让 Banner 承担新首页的视觉重心，同时把“我的收藏”放在首屏附近。收藏不再控制整页是否加载完成，但用户仍能快速进入熟悉内容。

### 2.2 各板块定义

#### A. 焦点 Banner

- 数据只来自声明 `homeFeed` 能力的已安装插件。
- 宿主全局最多展示 5 张；多插件时先保证每个来源最多占 1 张，再进入第二轮补位。
- Banner 支持房间或分类两类原生目标；首期不支持任意外部 URL。
- 插件来源信息是否展示、如何展示由最终 UI 设计决定；宿主始终保留内部来源身份。
- 图片加载失败时显示静态占位和标题，不让 Banner 区域塌陷。
- `imageURL` 必须优先返回适合沉浸式大图的原始图或高清图，不得主动拼接 400 px 缩略图参数。以 iPhone 3x 屏为基准，建议图片至少 1600 px 宽、900 px 高；房间型 Banner 在 `roomCover` 可用时由宿主优先显示直播间高清封面，并将 `imageURL` 作为失败兜底。宿主会按实际 Banner 尺寸和屏幕倍率下采样并缓存原图，但不会把低清缩略图视为可恢复的高清资源。
- 支持手动翻页，并在前台每 6 秒自动轮播；用户手动翻页后重新计时，开启“减弱动态效果”时暂停自动轮播。
- 多张 Banner 使用首尾镜像页实现无缝无限循环，手动滑动与自动轮播跨过末页后都无动画回正到真实首项，页码只统计真实内容。
- 首页处于顶部时，下拉回弹按实际拖拽距离等比放大 Banner，并以底边为锚持续补偿纵向位移，使大幅下拉时图片顶边仍严格贴住屏幕顶部、不出现空隙；开启“减弱动态效果”时不执行额外缩放。
- Banner 左上角胶囊是平台切换器：列出全部声明 `homeFeed` 能力的已安装平台，多平台时提供“全部平台”聚合项；切换后 Banner 与插件推荐分区必须使用同一平台过滤状态。

#### B. 我的收藏

- 直接读取 `AppFavoriteModel.roomList` / `FavoriteLocalStore` 的本地快照，不等待云端和直播状态刷新。
- 首页横向展示建议最多 10 个，顺序保持稳定；“查看全部”进入现有完整收藏页。
- 本地收藏为空时不在首页保留空分区，Banner 后直接承接第一个插件直播分区，避免首屏出现大块无效留白。
- 直播状态刷新只更新卡片状态，不在刷新过程中重新排序。
- 分区标题旁显示轻量“正在更新”状态；不在每张卡上放转圈，不覆盖列表。
- 缓存状态尚未确认时允许显示上次状态，同时通过分区级文案说明正在更新。
- 刷新失败保留上次结果，并提供手动重试；失败不影响其他首页分区。

#### C. 插件推荐分区

- 首期只支持标准房间横滑列表，统一复用宿主房间卡片和播放入口。
- 标题、房间数据和可选推荐说明由插件返回，字体、颜色、卡片比例和动画由宿主决定。
- 每个分区明确绑定一个 `pluginId`，一个插件失败不会删除其他插件内容。
- “查看全部”首期只允许跳转到插件返回的标准分类目标。
- 个性化逻辑留在插件内部；宿主不合并或上传用户跨插件行为。

#### D. 继续观看

- 数据来自本地 `HistoryModel.watchList`，首屏可立即显示。
- 按最近观看顺序展示，不因插件首页刷新而变化。
- 对应插件已卸载或不可用时，可展示历史信息但禁用直接播放，并提示重新配置插件。

#### E. 我的平台

- 由宿主根据已安装插件生成，仅作为入口，不属于插件推荐内容。
- 展示插件名称、图标、可用状态；点击进入现有平台详情页。
- 不在首页展示安装源、商店或“推荐插件”。AngelLive 不承担插件分发角色。

### 2.3 首期不做

- 插件自定义首页布局、字体、颜色、卡片尺寸和动效。
- HTML / WebView 首页、远程 SwiftUI、JSON UI DSL。
- 自动播放 Banner 视频、无限循环装饰动画，以及不响应“减弱动态效果”的持续运动。
- 宿主把收藏/历史打包给插件做跨平台画像。
- 宿主自行抓取平台数据或内置推荐算法。
- 为首页协议捆绑任何真实平台插件；仓库内只允许协议测试夹具。

## 3. 插件协议兼容方案

### 3.1 核心决策:不提升全局 `apiVersion`

现有运行时要求插件 `apiVersion` 与 `JSRuntime.supportedAPIVersion` **严格相等**，当前均为 1。如果仅为首页可选能力把全局版本提升到 2，所有旧插件都会在加载阶段被判定不兼容。

因此首期采用:

- 插件运行时继续声明 `apiVersion: 1`。
- 在现有能力表新增可选能力 `homeFeed`。
- 新增可选函数 `getHomeFeed(request)`。
- 首页响应自己携带 `schemaVersion: 1`，以后只升级首页数据结构，不连带升级整个插件运行时。

这与现有 `capabilities` 声明 + 函数扫描兜底机制保持一致。

### 3.2 能力声明

建议插件清单增加:

```json
{
  "apiVersion": 1,
  "capabilities": {
    "categories": "available",
    "rooms": "available",
    "playback": "available",
    "homeFeed": "available"
  }
}
```

宿主侧变更:

```swift
public enum PlatformFeature: String, CaseIterable, Sendable {
    // existing cases...
    case homeFeed
}

// PlatformCapability.featureFunctionNames
(.homeFeed, ["getHomeFeed"])
```

能力判定顺序:

1. 有 `capabilities.homeFeed` 时以显式声明为准。
2. 旧式清单没有 `capabilities` 时，可扫描入口脚本是否存在 `getHomeFeed`。
3. 两者都不存在时视为“不支持首页”，插件其他功能照常可用。
4. 声明可用但运行时缺少函数时，只记录该插件首页能力错误，不使插件整体加载失败。

### 3.3 请求结构

```json
{
  "schemaVersion": 1,
  "locale": "zh-Hans-CN",
  "region": "CN"
}
```

首期只传协议协商和本地化所需字段:

| 字段 | 必需 | 说明 |
|---|---:|---|
| `schemaVersion` | 是 | 宿主当前理解的首页响应版本 |
| `locale` | 是 | BCP 47 语言标签，用于插件生成展示文字 |
| `region` | 否 | 用户系统区域；不可作为稳定设备标识 |

不传设备 ID、广告 ID、完整设备型号、收藏、历史或其他插件列表。插件需要登录态时继续使用现有隔离会话能力，不在请求体里传 Cookie。

### 3.4 响应结构

首期建议把插件协议控制在“Banner + 房间分区”，不要一开始设计成无限扩展的页面描述语言。

```json
{
  "schemaVersion": 1,
  "revision": "opaque-feed-revision",
  "generatedAt": "2026-08-21T14:00:00Z",
  "ttlSeconds": 900,
  "banners": [
    {
      "id": "banner-001",
      "imageURL": "https://example.invalid/banner.jpg",
      "title": "今晚热门直播",
      "subtitle": "可选副标题",
      "badge": "直播中",
      "target": {
        "type": "room",
        "room": {
          "userName": "主播名",
          "roomTitle": "房间标题",
          "roomCover": "https://example.invalid/cover.jpg",
          "userHeadImg": "https://example.invalid/avatar.jpg",
          "liveState": "1",
          "userId": "user-id",
          "roomId": "room-id",
          "liveWatchedCount": "12.3万"
        }
      }
    }
  ],
  "sections": [
    {
      "id": "for-you",
      "kind": "rooms",
      "title": "为你推荐",
      "subtitle": "可选说明",
      "personalized": true,
      "items": [
        {
          "id": "room-id",
          "room": {
            "userName": "主播名",
            "roomTitle": "房间标题",
            "roomCover": "https://example.invalid/cover.jpg",
            "userHeadImg": "https://example.invalid/avatar.jpg",
            "liveState": "1",
            "userId": "user-id",
            "roomId": "room-id",
            "liveWatchedCount": "12.3万"
          },
          "reason": "你最近看过同类内容"
        }
      ],
      "seeAllTarget": {
        "type": "category",
        "category": {
          "id": "category-id",
          "parentId": "parent-id",
          "title": "分类名",
          "icon": "",

        }

```

数据模型建议:

```swift
public struct PluginHomeFeedDTO: Decodable, Sendable {
    public let schemaVersion: Int
    public let revision: String?
    public let generatedAt: Date?
    public let ttlSeconds: Int?
    public let banners: [PluginHomeBannerDTO]
    public let sections: [PluginHomeSectionDTO]
}
```

`personalized` 放在分区而不是整个响应上，避免一个插件的普通热门榜单被误标为个性推荐。`banners` / `sections` 缺失时按空数组处理。房间字段继续沿用当前 `PluginRoomDTO` 的兼容口径，避免首页和分类页出现两套房间模型。宿主在解码后补上插件对应的 `LiveType`，再生成 `LiveModel`。

### 3.5 首期目标类型

| 类型 | 用途 | 允许字段 |
|---|---|---|
| `room` | Banner / 推荐卡进入播放详情 | 现有房间 DTO |
| `category` | 分区“查看全部”进入现有分类列表 | 现有分类 DTO |

首期不支持 `externalURL`、自定义脚本回调和任意路由字符串。以后若确实需要，应新增明确能力和白名单目标类型，不能让插件绕过宿主导航直接控制页面。

### 3.6 宿主校验和限额

| 项目 | 建议规则 |
|---|---|
| `schemaVersion` | 首期仅接受 1 |
| Banner | 单插件最多取 5 张，聚合后全局最多 5 张 |
| 分区 | 单插件最多 8 个 |
| 分区房间 | 每区最多 20 个 |
| TTL | 默认 15 分钟；宿主限制在 60 秒至 24 小时 |
| 图片 URL | 仅接受 `https`；开发调试可按现有网络策略例外处理 |
| 稳定 ID | 必填；宿主最终命名空间为 `pluginId:kind:itemId` |
| 文本 | 去首尾空白并限制长度，超出由宿主截断 |
| 未知分区类型 | 丢弃该分区，不丢弃整个首页响应 |
| 单个坏元素 | 跳过该元素并记录诊断，不让整批解码失败 |

实现上不要直接用“未知枚举值即抛错”的默认解码方式。分区和目标应采用可容错解码，并对数组元素逐个解码，保证未来插件多返回一个新类型时，旧宿主仍能显示认识的部分。

### 3.7 兼容矩阵

| 宿主 | 插件 | 结果 |
|---|---|---|
| 旧宿主 | 旧插件 | 保持现状 |
| 新宿主 | 旧插件 | 旧插件正常工作，但不贡献首页推荐内容 |
| 旧宿主 | 新插件 | 未知 `homeFeed` 清单字段被忽略；原有分类/播放能力继续工作 |
| 新宿主 | 新插件 | 协商成功后显示首页内容 |
| 新宿主 | 更高首页 `schemaVersion` | 使用上一次兼容缓存；无缓存则只跳过该插件首页分区 |
| 新宿主 | 声明能力但函数缺失/超时 | 该插件首页失败，插件其他页面仍可使用 |

新插件如果只是“额外支持首页”，不必通过 `minHostVersion` 排斥旧宿主。只有插件整体已经依赖新宿主且旧宿主无法运行时，才提高 `minHostVersion`。

## 4. 宿主架构与数据流

### 4.1 组件拆分

```text
HomeView (SwiftUI)
    │ 只根据状态渲染
    ▼
@MainActor @Observable HomeViewModel
    ├─ HomeComposer                 合并插件分区和本地模块
    ├─ AppFavoriteModel             收藏快照/状态刷新
    ├─ HistoryModel                 本地历史
    └─ PluginHomeFeedService
           ├─ LiveParse plugin call
           ├─ tolerant decoder
           └─ HomeFeedCache actor   每插件独立磁盘缓存
```

- `HomeViewModel` 只负责界面状态和用户动作，标记 `@MainActor`。
- 插件调用、JSON 解码和磁盘缓存放到 actor / 后台任务，不占用主线程。
- `HomeComposer` 只接收不可变快照，生成稳定的首页分区 ID。
- 每个插件都有独立的加载、缓存、过期和错误状态，不设一个控制整页的 `isLoading`。

### 4.2 启动流程:缓存先行，后台更新

```text
进入首页
  ├─ 立即读取本地收藏、历史和已安装插件列表
  ├─ 并发读取每个插件的磁盘首页缓存
  ├─ 首次组合并显示页面
  └─ 后台刷新
       ├─ 插件首页请求（限制并发数）
       └─ 收藏直播状态刷新（独立任务）
            ↓
       每个分区单独、稳定地更新
```

推荐策略:

- 插件刷新并发上限先设为 3，防止大量已安装插件同时抢网络、CPU 和 JSRuntime。
- 缓存未过期时也可做低优先级 revalidate，但不显示全页刷新状态。
- 同一插件重复进入首页时合并进行中的请求。
- 手动下拉刷新可以请求所有来源，但仍按分区陆续完成，不清空旧内容。
- App 进入后台时不为首页维持刷新；回到前台根据 TTL 判断是否更新。

### 4.3 缓存键与失效

建议缓存键至少包含:

```text
pluginId + pluginVersion + homeSchemaVersion + sessionContextRevision
```

- 不把 Cookie、Token 或用户 ID 明文写进缓存键。
- 插件升级、禁用、卸载或登录态切换时清除该插件首页缓存。
- `revision` 只作为响应去重标识，不能跨插件比较。
- 请求失败时保留最近一次兼容缓存，并标记为 stale；不因一次失败清空首页。
- 插件卸载后立即删除其分区和缓存，不能留下无法解释来源的推荐内容。

### 4.4 多插件聚合规则

- 首页骨架顺序由宿主决定，插件只能提供自己的 Banner 和分区。
- Banner 按插件轮询取样，避免一个插件占满全部位置。
- 插件分区优先维持上次成功顺序；刷新时不因响应先后改变位置。
- 同一房间的去重键使用现有口径 `liveType + roomId`，不能只用 `roomId`。
- 跨插件看似相同的房间不做猜测式合并，因为播放能力、身份和数据来源可能不同。
- 插件只能修改自己的缓存和分区，不能声明本地“收藏”“历史”“我的平台”模块。

## 5. 页面布局规范

### 5.1 iPhone

- 根视图使用 `NavigationStack` + `ScrollView` + `LazyVStack`，分区按需创建。
- Banner 在 iPhone 上横向占满容器，图片保持原比例并使用裁切填充形成约容器宽度 90% 的沉浸高度；底部渐变必须过渡到页面背景色，让首个分区标题自然进入渐变尾部，而不是以黑色硬切结束。
- Banner 左上角平台切换器使用系统 Regular Liquid Glass 胶囊，显示插件包提供的平台图标且不额外显示下拉箭头；“全部平台”使用最多三个平台图标轻量叠放。房间型 Banner 在画面下半部只显示房间名与主播头像/主播名，不重复展示平台名；分类型 Banner 使用插件标题和可选副标题。分页指示器使用紧凑的玻璃胶囊承载短线与圆点，并固定在底部居中，三者不能互相遮挡。
- 横滑卡片沿用 `LiveRoomCard`；同一分区内必须等宽、等高并对齐，不允许单卡交替缩放或下沉。层次通过分区规格区分：首个重点分区使用统一宽卡，后续分区可使用统一紧凑卡。
- 分区间距、卡片圆角、标题层级复用现有平台页和收藏页视觉语言。
- 第一 Tab 从“收藏”改名为“首页”，建议图标 `house.fill`；完整收藏页从首页“查看全部”进入。

### 5.2 启动缓存与加载态

- 首页采用 stale-while-revalidate：启动先从 `Caches/AngelLive/home-feed-v1.json` 恢复已校验的聚合快照，再在后台刷新插件数据。
- 缓存即使超过插件 TTL 也可作为启动快照展示；TTL 只决定刷新时机，不能让首页退回白屏。网络失败时保留对应插件的旧快照。
- 刷新成功后以原子写入替换缓存；缓存只保存有边界的结构化数据和图片 URL，图片磁盘缓存继续由 Kingfisher 管理。
- 首次安装没有缓存时，加载态必须复刻实际 Banner、分区标题与 `LiveRoomCard` 的尺寸，用中性色骨架和轻量 shimmer 展示；禁止纯白等待页、彩色大色块和居中转圈。

### 5.2 iPad 与横屏

- 使用容器宽度决定布局，不根据设备型号写死分支。
- Banner 设置合理最大宽度，避免在大屏被无限拉高。
- 房间区域可切换为 adaptive grid 或更宽的横滑列表；同一分区 ID 和导航目标在尺寸变化时保持不变。
- 支持分屏实时变宽/变窄，旋转和窗口调整不能重建整份首页状态。

### 5.3 可访问性与视觉约束

- 标题、来源、状态使用语义字体，支持 Dynamic Type；不要用固定字号压缩重要文字。
- 卡片点击目标至少 44 × 44 pt，按钮有明确 VoiceOver 标签。
- 图片上的文字要有稳定遮罩，不能依赖某张封面恰好够暗。
- 不能只用颜色表达“直播中 / 已下播 / 更新失败”。
- 深浅色模式下均使用系统层级色；插件主题色只能作为受限点缀，不能覆盖可读性规则。
- 来源信息如果展示，不得因字体放大或窄屏被完全隐藏。

## 6. 动效规范

动效服务于“进入、刷新、打开播放”三个状态，不做纯装饰。默认适配“减弱动态效果”。

| 场景 | 推荐动效 | 时长 / 曲线 | 限制 |
|---|---|---|---|
| 本地/缓存首屏出现 | 直接显示；必要时只做整体淡入 | 0.15–0.20 s `easeOut` | 不做逐卡片长队列入场 |
| 某插件首次返回分区 | 分区 `opacity` + `y: 8` | 约 0.25 s `smooth` | 只动画新分区，不推动整页反复跳动 |
| 缓存替换为新数据 | 分区内部交叉淡化 | 0.20–0.25 s `easeInOut` | 稳定 ID；不清空再插入 |
| Banner 翻页 | 固定全宽画布 + 6 秒自动推进 | 页面始终铺满视口且不参与缩放，避免全宽相邻页之间露出底色；自动推进约 0.45 s `smooth` | 手动翻页后重新计时；后台和减弱动态效果下暂停 |
| Banner 视差 | 卡片横移时，图片层在裁切框内反向运动，形成明确的前后层速度差 | 参考 Demo 将页面层和图片层分离：`visualEffect` 只读取固定全宽页面在横向滚动视口中的 `minX`，归一化为 `-1...1` 的分页进度；16:9 图片保持原画布比例并等比放大到 `1.16×`，再于安全余量内反向位移，避免全宽模式露出底色 | 不缩放或倾斜页面；不写入滚动状态；不叠加纵向漂移；减弱动态效果下关闭 |
| 卡片按下 | 缩放至约 0.97 + 轻触觉 | 短 `snappy` | 减弱动态效果时取消缩放 |
| 卡片进入播放器 | iOS 18+ 复用现有 zoom transition | 系统转场 | iOS 17 使用现有标准导航/全屏转场 |
| 收藏正在刷新 | 标题旁小型同步符号旋转/脉冲 + 文案 | 仅刷新期间 | 不让每张卡转圈，不遮挡列表 |
| 收藏刷新完成 | 同步符号一次性替换为勾 | 一次 `replace` | 自动刷新不频繁弹 Toast |
| 图片加载完成 | 占位图到封面淡化 | 约 0.20 s | 不使用持续 shimmer |
| 下拉刷新 | 系统 `refreshable` 反馈 | 系统 | 保留旧内容，不回到全屏 Loading |

明确禁止:

- Banner 自动视频播放。
- 无限呼吸、漂浮、粒子和持续闪烁；视差只能用于 Banner 图片层并限制位移。
- 对几十张卡片依次 stagger，导致用户等待动画而不是看到内容。
- 刷新时整页重新排序、滚动位置回顶或卡片尺寸跳变。
- 用动画代替文字状态；动画关闭后仍必须看懂“更新中 / 失败 / 已完成”。

版本降级:

| 系统版本 | 行为 |
|---|---|
| iOS 17 | 核心首页、标准导航、基础淡入和系统 `ProgressView` |
| iOS 18+ | 可复用现有卡片到播放器 zoom transition、合适的 symbol effect |
| iOS 26+ | 沿用系统 Tab 收缩和系统材质；不为首页强制堆叠自定义玻璃效果 |

## 7. 页面状态与失败降级

### 7.1 分区状态

每个数据来源独立维护:

```swift
enum HomeSectionPhase {
    case cached
    case loading
    case refreshing
    case ready
    case stale(message: String?)
    case failed(message: String)
}
```

视图规则:

- `cached` / `refreshing`:显示现有内容，只在标题处提示。
- `loading`:仅当该分区从未有内容时显示尺寸稳定的占位。
- `stale`:继续显示旧内容，可提供重试。
- `failed`:只展示该来源的紧凑错误，不占满页面。

### 7.2 典型场景

| 场景 | 首页行为 |
|---|---|
| 没有安装插件 | 显示本地收藏/书签、历史、直接播放入口和配置说明；不显示平台 Banner/推荐 |
| 插件没有 `homeFeed` | 不进入首页聚合，分类、搜索和播放功能保持原样 |
| 一个插件超时 | 使用该插件旧缓存或隐藏其空分区，其他来源继续更新 |
| 全部插件失败且无缓存 | 首页仍保留收藏、历史和工具入口，不显示全页错误 |
| 收藏状态刷新很慢 | 收藏快照可操作，标题显示“状态更新中”，首页其余内容不受影响 |
| 插件升级后协议不兼容 | 清理该版本缓存，记录诊断，只跳过该插件首页内容 |
| 登录态切换 | 清理该插件旧会话缓存，其他插件和本地模块不变 |

无插件空态建议文案:

> AngelLive 是播放器工具。平台内容由你自行安装的插件提供；当前仍可使用直接播放、本地书签和历史记录。

## 9. 测试清单

### 9.1 协议与兼容

- 新宿主加载完全不含 `homeFeed` 的旧插件。
- 入口脚本有 `getHomeFeed`、清单无 `capabilities` 时可正确探测。
- 清单声明可用但函数缺失时只报首页错误。
- 响应含未知顶层字段时继续解码。
- 单个未知分区、坏 Banner 或坏房间不会丢弃整个响应。
- `schemaVersion` 过高时回退到兼容缓存。
- 房间稳定身份仍为 `liveType + roomId`。
- 首页请求不包含收藏、历史、Token、Cookie 或其他插件信息。

### 9.2 缓存与状态

- 缓存命中后立即显示，刷新不会清空旧内容。
- TTL 最小值、最大值和默认值生效。
- 插件升级、卸载、禁用、登录态切换后只清理对应缓存。
- 多插件并发时一个超时不阻塞其他插件。
- 响应返回顺序变化时首页分区位置保持稳定。
- 收藏刷新时卡片不跳序，滚动位置不变化。

### 9.3 UI 与性能

- 无插件、无缓存、有缓存、刷新中、部分失败、全部失败 Preview / 截图测试。
- iPhone 小屏、Max、大字体和 iPad 分屏布局。
- 减弱动态效果下没有缩放、位移和 zoom 依赖，状态仍清楚。
- 5 张 Banner、多个分区和约 100 张卡片时保持懒加载。
- 图片解码和 JSON 解码不阻塞主线程。
- 有缓存情况下测量首个有意义内容时间，目标不超过 300 ms。

## 11. 最终判断

这个方案是可行的，而且比继续把收藏页当默认首页更符合 AngelLive 的工具定位:

- **速度更合理:**插件首页聚合可以一次返回并缓存；收藏逐房间状态刷新退到后台，不再决定首屏速度。
- **职责更清楚:**插件提供数据，AngelLive 提供统一、安全、原生的播放器体验。
- **兼容成本可控:**不提升全局 `apiVersion`，旧插件无需修改，新能力按插件逐步加入。
- **体验更稳定:**本地收藏和历史秒显，各分区独立刷新，失败和慢请求不再拖住整页。
- **扩展不过度:**首期只定义 Banner、房间分区和两类原生目标，先把真正需要的首页能力做稳，再评估更多类型。

实施时最重要的验收句只有一句:

> **首页可以展示插件返回的内容，但 AngelLive 永远只是播放器宿主，不成为插件提供方或内容推荐方。**
