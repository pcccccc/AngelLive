# tvOS 收藏自动刷新循环

> 记录日期：2026-09-27
> 状态：已完成日志与代码定位，待修复及验证。
> 基线：`159f2a8`。范围为 tvOS FullUI 自动刷新入口与共享收藏身份/刷新逻辑。

## 现象与影响

收藏反复发起自动刷新，即使上一轮已经完成，仍继续获取整批房间状态。网络超时让每轮耗时约 20 秒，但不是反复启动的充分原因。多轮请求增加网络负担，并重复输出失败摘要。

本次只保存脱敏统计，不提交用户原始日志、房间标识、插件私有响应或网络地址。

## 已定位的触发链

1. `TV/AngelLiveTVOS/Other/ContentView.swift` 的 `topShelfRefreshIdentity` 使用 `roomList.map(\.id).sorted()`；`LiveModel.id` 由来源标识与 `roomId` 组成。
2. `.task(id: topShelfRefreshIdentity)` 内调用 `syncWithActor()`。成员数量或房间 ID 改变会重启这个网络同步入口。
3. `AppFavoriteModel.flushRoomPatches` 将详情结果写回收藏，再执行多维身份去重；刷新本身可能改变集合。
4. `FavoriteSyncEngine.fullReconcile` 会从服务器补入本地缺失成员；日志明确记录了一次 157 补回 164。
5. `matchesRefreshedInputs` 比较收藏 key 集合。集合变化会令一分钟自动刷新有效期失效；等待共享自动任务的调用者还会在不匹配时再次调用同步。

因此存在“刷新/对账改变集合 → TV 任务重启 → 再次同步刷新”的反馈链。这解释了为什么不是单纯重复打印。

- 将 Top Shelf 展示发布与收藏网络刷新触发解耦；列表增量更新继续发布 Top Shelf，但不因此再次请求整批收藏。
- 在正确的共享层维护收藏稳定身份，状态更新不得悄悄合并不同收藏。遵守插件 manifest 的身份及刷新保留规则。
- 不靠提高超时、降低并发、屏蔽日志或永久禁止自动刷新掩盖问题。
- 不修改 ShellUI、播放器、账号凭证或云端用户数据；不清空缓存或收藏，不为具体内容平台写特殊分支。
