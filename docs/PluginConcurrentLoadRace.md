# 插件首次并发加载竞态

## 故障与定位

2026-09-28，用户报告同一插件概率性停在初始化 HTTP 成功之后，房间列表长期不返回。详情调用也可能耗尽收藏刷新预算后被取消。HTTP 成功日志本身只证明收到响应，不能证明 JavaScript 的后续代码已经执行。

`LiveParseLoadedPlugin.load()` 原来只有完成标记 `isLoaded`。actor 在每次 `await runtime.evaluate(...)` 时允许其他调用进入，因此多个首次调用可以在同一个 JSContext 中重复、交错执行预加载脚本；actor 隔离不等于整个异步方法不可重入。

某类插件的预加载顺序为：环境脚本保存原生 Promise → 第三方 SDK 临时改写 Promise → 绑定脚本恢复原生 Promise。两个加载任务可以形成以下合法交错：

1. A 的环境脚本保存原生对象。
2. A 的 SDK 改写 Promise 及其原型方法。
3. B 的环境脚本把已经改写的对象覆盖写入同一保存槽。
4. A 的绑定脚本读取被覆盖的保存槽，无法恢复原生实现。

随后第一个入口脚本仍能加载成功，但 HTTP 回调完成后，原来的 async/await 链可能不再继续。其他加载任务再次求值入口中的顶层 `const` 还可能报重复声明。运行时一旦被污染，单纯重试业务调用不会重新执行正确的初始化。

## 原生 JavaScriptCore 对照实验

在本机系统 JavaScriptCore 上加载用户提供的完整预加载脚本与入口，使用合成 HTTP 响应；保留真实签名计算，不访问外部服务或真实凭据。显式构造上述合法交错，并对每组发起 5 次列表调用。以下为三秒观察窗口内的计数，不代表实机验证。

| 条件 | 初始化请求 | 后续列表请求 | 完成调用 |
| --- | ---: | ---: | ---: |
| 原异步链，单次有序加载 | 5 | 5 | 5 |
| 原异步链，交错加载 | 5 | 0 | 0 |
| 交错加载，仅合并初始化请求 | 1 | 0 | 0 |
| 交错加载，直接回调并合并初始化 | 1 | 5 | 5 |
| 交错加载，仅直接回调 | 5 | 5 | 5 |

交错组的全局 Promise 与 `Promise.prototype.then` 均不再等于初始化前保存的原生对象；有序组保持相等。实验区分了请求合并和直接回调的作用：合并不能恢复已污染的等待链，直接回调可以绕开这一链路。它证明当前代码存在能够产生报告症状的具体机制；原始用户会话未记录预加载阶段，不能据此声称已经捕获该会话的实际调度顺序。

## 修复边界

共享加载器应在第一次挂起前登记唯一的进行中加载任务，后续调用等待同一任务，保证预加载和入口对一个 runtime 只初始化一次。成功后继续沿用已加载标记；失败清理进行中任务，保持现有错误与重试语义。某个业务调用取消不能取消其他调用共同等待的初始化。

不修改 HTTP 协议、插件版本选择、凭据处理或页面加载策略，不通过增加超时掩盖初始化竞态。回归 fixture 使用中性脚本，覆盖并发初始化一次、成功后复用、失败后重试和等待者取消。
